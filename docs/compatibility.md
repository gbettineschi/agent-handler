## Protocol boundary

Desktop IPC is undocumented. Agent HUD Open's versioned implementation is the reference, with a pinned upstream revision and notices in [THIRD_PARTY_NOTICES.md](../THIRD_PARTY_NOTICES.md). This does not give the protocol an upstream stability promise.

Before submitting, the adapter verifies the owner, current turn and exact question from its current stream. It validates the owner/method/turn in the receipt. The host submission method does not offer an atomic expected-question compare-and-set; a race remains between preflight and submission. Unknown delivery is retained as uncertain and never retried automatically.

Running-turn answers use the native steer method. Completed-turn answers use the native start-turn method with inherited host settings; they do not override permissions, model or collaboration mode. A valid accepted receipt can settle a temporarily unavailable request only with the same epoch and fingerprint.

Approvals reconcile in their own scope, independently of question-history completeness. The parser binds the full native request and complete relevant settings into the displayed fingerprint. A native approval `ok` response is only a dispatch acknowledgment; even a missing request can receive it. The send remains uncertain until authoritative withdrawal closes the card, and cannot be retried. The owner's native pending server-request queue establishes the human prompt: a recognized automatic turn reviewer does not suppress a real manual fallback. Automatic-review progress notifications alone never create approval controls. Unknown reviewer/policy/schema values remain disabled. Stdin approvals are not presented as command execution. An actual pending command/MCP request without a validated response mapping retains its chat with a scoped Review in Codex notice, including when an older unavailable card remains. Missing request data alone does not claim a human approval. This is not exhaustive detection of every unsupported request kind.

Only stream version 11 and recognized complete question shapes become actionable. A version change, malformed state, revision gap or disconnection disables answering. Local permissions and peer UID are checked; the app does not change agent permission settings. Foreign-UID rejection is implemented, but a separate-UID runtime test has not been performed.

## Limits

- At most 16 followed conversations and 128 unresolved requests.
- Frames at most 128 MiB; supported content fields at most 16 KiB.
- Native snapshots selectively discard unused turn/item metadata during parsing, before the 200,000 retained-node limit. Discarded-object duplicate-key validation has a separate 1 MiB temporary key budget. Patch values retain the raw node cap; a sufficiently large replacement patch can still require conservative resynchronization.
- Conservative retained-tree accounting: 8 MiB per conversation, 64 MiB across the followed set, depth under 128. These are projection budgets, not exact RSS limits; receive buffers, parser temporaries and copy-on-write versions add transient memory.
- Unused item and turn metadata fields are discarded before retained-budget admission. Identity, question content and accepted-answer envelopes stay intact; markers preserve paths for later native updates. Required oversized content is still unsupported.
- Completed questions remain visible across consecutive native reply turns and recognized tool-output or context-compaction continuations. Neither continuation's contents can answer nor end the earlier group. A new ordinary native user prompt ends that group; interrupted/failed turn boundaries remain terminal. Gaps, partial item history, empty hydrating turns and unknown input types cannot establish withdrawal. Source-local Skip/dismiss state is not a verified protocol signal.
- Candidate file metadata is checked every five seconds; SQL runs when metadata changes or at least every sixty seconds. No periodic full transcript scan.
- Verified owner IDs retain presentation-only metadata through source gaps; they never supply a fabricated turn or response target. Ordinary unknown sessions are hidden immediately, while tracking continues and fresh activity makes them visible again. Actual unresolved requests and positively observed source-only waits remain visible through gaps, including missing turn IDs. Only Codex fallback requests and Claude read-only permission facts create remembered source waits; stale activity from a resolved typed Codex request cannot create one. Pending requests/source-only waits are selected first, then explicit IDs and active/unresolved owned sessions before ordinary recent candidates. A previously clear terminal session invalidated by owner loss does not permanently occupy an active slot. The 16-conversation bound remains.
- Ten-second connection/answer deadline, thirty-second frame deadline and capped recovery/reconnect cadence.
- Activity records describe the latest native Work turn, not completion of an entire agent tree or an external follow-up queue. Visible pending submissions, active goals and queued messages prevent a completed classification. An optional panel opening follows newly observed terminal transitions; this is not durable notification delivery. Ordinary Chat/cloud-only Claude activity sources remain future work.
- Claude audit observation is local and read-only: at most 512 discovered sources, 16 followed sources, 256 KiB read per source/tick and 512 KiB per record/metadata file. Existing files start at EOF. Unknown records, partial lines, backlog, source loss, rewriting/truncation and unreadable inputs disable current classification. Audit order and SDK session ID correlate facts; no native atomic turn/response targeting or audit-HMAC verification is claimed. A quiet log cannot prove the individual runtime is alive; the surviving Desktop process is only an availability check.

Limit or compatibility failures preserve existing unresolved cards as unavailable. Some previously unseen requests may remain undiscovered; use the source app. Settings → Connection details and the read-only probe distinguish missing connections, timeouts, refused handshakes, absent owners, unsupported stream versions, retained-state capacity, state resynchronization and independent question/approval/activity parsing failures. These are presentation-only fixed reason codes and counts; they do not establish response authority or print native content. Frame/JSON decoding failures and decoder budgets still share an unreadable-or-oversized-data reason; the report does not guess their exact cause. Counts can overlap and the probe remains a sample.

After host updates: run tests, run the read-only probe, then complete the manual acceptance checklist before treating responses as verified on that build. Do not patch around a changed protocol by guessing IDs or accepting an unrecognized receipt.

The pinned stream’s observed `imageView` item is recognized as a non-question item after a native reference-image check on 2026-10-20. Its embedded content/questions cannot create or settle requests. This does not broaden support to arbitrary unknown item types.
